## 2026-10-01 — Тиждень 5, день 3: гібридний пошук (BM25 + dense)

**Мета:** полагодити два провали з дня 2 — лексичний розрив і нерозрізнювальні scores.

---

### Теорія

**Чому dense не всесильний.** Embedding стискає зміст у 384 числа; при такому
стисненні втрачається точність окремих термінів. Вектор вловлює «це про
масштабування в attention», але не тримає, що слово було `scale`, а не `divide`.

**BM25** працює протилежно: не розуміє сенсу, зате точно знає, які слова де є.
- TF — чим частіше слово, тим краще, але з насиченням
- IDF — чим рідкісніше слово в корпусі, тим цінніше (`the` не розрізняє нічого)
- нормалізація довжини — довгий документ штрафується
Слабкість дзеркальна: не знайде синоніми (`car` не знайде `automobile`).

**RRF (Reciprocal Rank Fusion)** — злиття за позиціями, не за оцінками:
`RRF(d) = Σ 1/(k + rank_i(d))`, k=60.
Потрібен, бо шкали несумісні — у моєму прогоні dense дав 0.84–0.90,
BM25 2.6–5.2, складати їх безглуздо. Ранги порівнянні завжди.

**Реалізація:** Qdrant, дві назви векторів в одній точці (`dense` + `bm25`),
`fastembed` для sparse-векторів, `Prefetch` по 20 кандидатів з кожного методу
→ RRF → топ-5.

---

### Головне відкриття: markdown-розмітка ламає BM25

Токенізація трьох написань одного терміна:
```
d_k   → 1923612452
dk    → 334211879
_dk_  → 1954487834
```
**Три різні токени.** У документі `_dk_` (markdown-курсив), у запиті `d_k` —
збігу немає взагалі.

Тому BM25 знаходив `attention#11` не через ключовий термін, а через загальне
слово `divide`. А `attention#25` (Optimizer) вигравав через `square root`
у формулі learning rate. Обидва результати — випадкові збіги.

**Фікс:** `clean_text()` перед індексацією — зняти `<sup>`, `<u>`, `~~`, `**`,
і головне `_([A-Za-z0-9]+)_ → \1` (знімає курсивні підкреслення навколо термінів).

**Вимір, запит `"why divide by square root of dk"`:**

| | до очищення | після |
|---|---|---|
| BM25 результатів | 2 | 5 |
| BM25 #1 | attention#25 (хибний) | attention#11 (правильний) |
| чанк із відповіддю (#12) | не в топ-5 | #3 у гібриді |
| dense | розмитий | **без змін** |

→ розмітка в індексі робить ключові терміни **невидимими для лексичного пошуку**
→ dense розмітка не заважає: кілька символів губляться при стисненні в 384 числа
запит із точними термінами, яких dense не знає  → BM25 рятує
запит із синонімами без термінів                → dense рятує
RRF в обох випадках розбавляє результат переможця шумом того, хто провалився

### Уточнення про те, чому провалюється dense

Два запити на тій самій колекції:

```
"scaled dot product attention"      → 0.8991…0.8425, усі attention, правильні
"why divide by square root of dk"   → 0.8425…0.8299, усі lora, жодного релевантного
```

Розкид у другому — **0.013**. Вектори майже не розрізняються, тобто вектор запиту
опинився «ніде», і топ-5 — фактично випадкові точки фонової схожості.

Різниця між запитами: перший містить 4 технічні терміни, другий — переважно
службові слова (`why`, `divide`, `by`, `square`, `root`, `of`) плюс `dk`,
яке e5 не знає.

→ **уточнення до висновку дня 2**: справа не тільки в «лексичному розриві»
  (різні слова про те саме), а в **щільності змістовних термінів у запиті**.
  Запит із загальних слів дає розмитий вектор незалежно від формулювання.

### Де гібрид гірший за кращий із двох методів

Знайдено (завдання 5), до очищення markdown:

```
BM25 сам:      attention#11 на 2 місці
гібрид (RRF):  attention#11 на 3 місці
```

RRF **опустив** правильний чанк, бо dense поставив на 2 місце `lora#67`,
якого BM25 узагалі не бачив.

→ RRF наївно довіряє обом спискам. Коли один метод повністю провалюється,
  його шум просочується в результат — просто тому, що займає високі позиції
  у своєму списку
→ **гібрид не панацея**: він розбавляє результат працюючого методу сміттям
  того, що зламався
→ саме це лікує reranker: дивиться на пару «запит-документ» і перевпорядковує
  за реальною релевантністю, а не за позиціями

Після очищення на тому самому запиті гібрид працює правильно: dense провалився,
BM25 спрацював, RRF узяв результат працюючого (attention#11 на #1,
чанк із відповіддю на #3).

### Bi-encoder проти cross-encoder

**Bi-encoder** (поточний пошук): чанк кодується у вектор при індексації,
запит — окремо при пошуку, зустрічаються лише через косинус.
```
запит → [384] ─┐
                ├→ cosine
чанк  → [384] ─┘
```
Перевага: вектори рахуються заздалегідь, пошук по мільйону миттєвий.
Ціна: модель кодує чанк, **не знаючи запиту** — мусить стиснути зміст
«про всяк випадок».

**Cross-encoder** (reranker): обидва тексти подаються **разом** в одну модель.
```
[запит + чанк] → модель → одне число
```
Attention бачить слова запиту й документа одночасно й зіставляє напряму —
може «зрозуміти», що `divide` у запиті і `scale` в документі тут про одне.
Ціна: окремий прохід моделі **на кожну пару**.

**Звідси двоступенева схема:** retrieval (швидко, грубо) → 30 кандидатів →
reranking (дорого, точно) → топ-3.

Модель: `cross-encoder/ms-marco-MiniLM-L-6-v2` (~90 МБ, англійська).
`bge-reranker-v2-m3` (2.2 ГБ) не брав через обмеження памʼяті.

### Результат на проблемному запиті

3. attention#12 +0.3409           3. attention#13   -3.6149

Reranker відновив тематичну звʼязність, якої не було ні в dense, ні в BM25,

**Головне — шкала:**
```
dense:     0.8425 … 0.8299    розкид 0.013
reranker:  -2.36  … -8.22     розкид 5.86    ← ×450
```
Це розвʼязує проблему дня 2 («поріг на абсолютний score не працює»).
З reranker'ом поріг стає можливим.

**Чому всі scores відʼємні:** `ms-marco` тренована як бінарний класифікатор
«релевантно/ні» й видає **логіти**. Відʼємний = ймовірність < 0.5. Домен інший
(короткі веб-сторінки проти абзаців наукової статті), тому модель занижує.
Ранжування при цьому коректне — зміщені абсолютні значення, не відносні.
→ **поріг треба калібрувати під свій домен**, а для цього потрібен eval-датасет

---

### Де reranker не допомагає

На простих фактичних запитах приріст мінімальний. `"how many attention heads
in the base configuration"`: hybrid поставив `attention#14` на 2 місце,
reranker на 1. Одна позиція.

Причини:
- корпус малий і однорідний (164 чанки, 3 статті) — релевантне й нерелевантне
  тут надто різні
- гібрид і так витягує правильне в топ-5, перевпорядковувати майже нічого
- запити переважно фактичні, з технічними термінами

→ reranker **перевпорядковує те, що знайдено**. Він проявиться там, де
  кандидатів багато і правильний глибоко в списку
→ і не може знайти те, чого немає в кандидатах — це його жорстка межа

---

### Ціна

```
retrieval:       77 ms   (не залежить від кількості кандидатів)
rerank 28 пар: 3827 ms   ← ×50
```

**Вплив `batch_size` (28 кандидатів фіксовано):**

| batch_size | час ms | ms на пару |
|------------|--------|------------|
| 1          | 1829.9 | 65.4       |
| 2          | 1960.4 | 70.0       |
| 4          | 1989.1 | 71.0       |
| 8          | 2272.1 | 81.1       |
| 16         | 3005.3 | 107.3      |
| 32         | 3007.5 | 107.4      |

→ на CPU **менший батч швидший**: +64% часу від bs=1 до bs=16
→ причина: великі тензори не вміщаються в кеш процесора, починається обмін
  із RAM. Той самий механізм, що memory-bound decode у тижні 2
→ плато після 16, бо кандидатів 28 — один батч замість двох
→ **на GPU було б навпаки**: vLLM давав ×71 на батчингу, бо карта простоювала 85%
→ третій випадок, коли та сама оптимізація дає протилежний ефект на різному
  залізі (разом із bf16 на AVX2 і квантизацією prefill vs decode)

**Налаштування для CPU-сервісу:**
```
28 кандидатів, bs=32:  3008 ms
28 кандидатів, bs=1:   1830 ms  (−39%)
10 кандидатів, bs=1:   ~650 ms  (−78%)
```

Повний пайплайн на CPU: retrieval 77 + rerank ~650 + LLM 3B (~200 токенів
на 15 tok/s ≈ 13000) ≈ **14 секунд на запит**.
→ аргумент за оренду GPU на тиждень 6, коли почнеться eval на десятках питань

### Мовчазний баг у вимірі

Перший замір показував, що час reranking **не росте** від prefetch=30 до 100.
Перевірка кількості кандидатів:
```
prefetch= 10 → 10 кандидатів
prefetch= 30 → 28
prefetch= 50 → 28
prefetch=100 → 28
```

Причина: `search_hybrid` має жорсткий внутрішній `prefetch=20` на **кожен
метод**, не повʼязаний із `top_k`. RRF зливає два списки по 20, перетин 12 →
`20+20−12 = 28` унікальних, більше взяти нема звідки.

→ фікс: `prefetch = max(20, top_k * 2)`
→ окремо: при 164 чанках у базі `prefetch=100` означає ранжування 60% корпусу —
  двоступенева схема втрачає сенс. Розумний діапазон тут 20–30
→ правильна метрика ціни — **мс на пару**, вона не залежить від розміру бази

**Третій мовчазний баг у вимірах за тиждень** (після колекції `rag_hybrid`
замість `rag_clean_md` і падіння Qdrant). Спільне: числа виглядали правдоподібно.

## 2026-10-02 — Тиждень 5, день 5: eval пошуку

**Задача:** усі висновки тижня були враженнями від 5–6 запитів. Рівно той стан,
із якого я виходив у тижні 4, перш ніж зробив golden-датасет: там «v3 краща»
перетворилось на 0.33 → 0.75, і виявилось, що v4 насправді регресія.

---

### Метрики пошуку

**Recall@k** — чи потрапив релевантний чанк у топ-k. Головна для RAG: якщо чанка
немає в топ-k, він не потрапить у промпт, і модель не відповість, хай яка розумна.

**MRR** — середнє від `1/позиція` першого правильного. Показує не «знайшлось»,
а «наскільки високо». Recall і MRR разом розрізняють два стани:
- `recall@5=1.0, MRR=0.3` → завжди знаходить, але глибоко → reranker допоможе
- `recall@5=0.5, MRR=0.5` → половину не бачить узагалі → лагодити retrieval

**nDCG@k** — враховує кілька релевантних із різною важливістю. Для цього корпусу
надлишкова, але назву знати.

---

### Датасет: 16 питань

Склад: фактичні, концептуальні, термінологічні, синонімічні, з таблиць,
по всіх трьох документах.

**Процес розмітки** для кожного питання:
```bash
grep -n -i "<ключове>" data/processed/<файл>.md        # знайти рядки
python -m src.inspect_chunks --file X --find "<фраза>"  # номер чанка
python -m src.show_chunk X <номер>                      # ПЕРЕВІРИТИ вміст
```

Третій крок обовʼязковий: слово в чанку є ≠ з чанка можна відповісти.

**Кожен третій еталон виявився неправильним при перевірці.** `d_model_base`
вказував на `attention#14` (там `dk = dv = dmodel/h = 64`, а не `512`),
`attention_function` на `#12` замість `#10`, `positional_encoding` на `#31`
замість `#18`.
→ якби не перевірив, отримав би провали в метриці й шукав причину в пошуку
  замість датасету

**Правило: перелічувати ВСІ релевантні чанки.** Для концептуальних питань
відповідь повторюється в абстракті, вступі й основному розділі. Один еталон =
заниження: пошук знайде інший правильний і отримає нуль.
Приклад: `lora_idea` — додав `lora#2`, MRR гібрида піднявся 0.588 → 0.619.

**Межа при виправленні:** додавати чанк тільки якщо з нього можна **дати
відповідь**, а не якщо він про ту саму тему. Інакше датасет підганяється
під систему, і метрика перестає міряти.

### Два типи помилок retrieval

```
            k=3    k=5    k=10
dense       0.69   0.69   0.94
bm25        0.62   0.75   0.81
```

**Dense знаходить майже все, але глибоко** (0.69 → 0.94 при переході на 10).
Семантична близькість розмита: релевантне потрапляє в широку область,
але ранжується погано.

**BM25 бінарний:** або знаходить одразу, або ніколи (0.75 → 0.81, далі нічого).
Терміни або збігаються, або ні.

→ це пояснює, чому reranker дає стільки: він лагодить саме ранжування,
  а не пошук

---

### Reranker: прогноз не справдився

Я очікував «приріст у MRR, але не в recall — він перевпорядковує знайдене».
Насправді recall зріс 0.75 → 0.94.

Причина: reranker працює не з топ-5 гібрида, а з **28 кандидатами**. Правильні
чанки були в кандидатах на 10–20 позиціях, і гібрид їх відсікав.

→ уточнене формулювання: reranker не знаходить нового, але **витягує з глибини
  те, що retrieval знайшов і закопав**. Різниця між «не може знайти відсутнє»
  і «не покращує recall» принципова.

**При k=3 reranker не постраждав взагалі** (0.94 на обох k): усе, що він
знаходив, було на перших трьох позиціях. А BM25 втратив 0.13 — часто ставив
правильне на 4–5 місце.

---

### Де гібрид гірший за кращий метод

```
k=10:  dense 0.94,  hybrid 0.88
```

Шуканий випадок знайдено. При великому `k` dense уже витягнув майже все,
а RRF підмішує BM25-кандидатів, які витісняють правильні dense-результати.

→ RRF корисний, коли треба зібрати найкраще з двох **коротких** списків,
  і шкідливий, коли один метод уже охопив усе
→ на малих k гібрид виграє (0.81 проти 0.75 при k=5), на великих програє

**Побічне спостереження:** гібрид дав 0.75 при `k=5` і 0.81 при `prefetch=10`
(той самий метод!). Причина — `prefetch = max(20, top_k*2)`: інший набір
кандидатів для RRF дає інший порядок.
→ кількість кандидатів у злитті — ще один параметр для налаштування

### big_model_params — провал, який пережив усе

Єдиний, що провалився в усіх методів при k=5. При k=10 reranker його витягнув.

Чанк `attention#30` містить **і підпис, і таблицю разом**:
```
Table 3: Variations on the Transformer architecture. Unlisted values are
identical to those of the base model...
| base | 6 | 512 | 2048 | 8 | ... | 65 |
| big  | 6 | 1024| 4096 | 16| ... | 213 |
```

У підписі є `Transformer`, `architecture`, `base model`. У таблиці є `params`, `213`.
І все одно не знаходиться.

**Причини:**
- **dense:** 70% чанка — числа й трубки розмітки. Осмислений підпис (400 симв)
  тоне в таблиці (900 симв) при усередненні в 384 числа
- **bm25:** запит `parameters`, у таблиці `params` — стемінг не зводить до
  одного кореня (та сама історія, що `d_k` vs `dk` у дні 3)

→ проблема **не в чанкінгу й не в парсингу**: інформація ціла, підпис на місці,
  слова є
→ проблема в **співвідношенні сигналу до шуму всередині чанка**
→ загальне правило: embedding погано працює на чанках зі змішаним вмістом,
  де структуровані дані переважають над текстом

**Окремо:** `attention#28` (розділ 6.1) містить фразу «The configuration of this
model is listed in the bottom line of Table 3» — чанк **посилається** на таблицю,
але не містить її. Для людини робочий ланцюжок, для пошуку тупик.
→ ще один тип проблеми: інформація розподілена між чанками, жоден сам
  по собі не дає відповіді

**Лікування (не перевірено):**
- індексувати підпис і таблицю окремо, звʼязок у метаданих
- контекстуальне збагачення: LLM описує таблицю реченнями при інжесті
- окремий індекс для табличних даних

## 2026-10-04 — Тиждень 6, день 1: генерація з контекстом

**Задача:** підключити LLM до пошуку. Pipeline: питання → hybrid+rerank →
3 чанки в промпт → відповідь із цитуванням.

### Структура RAG-промпта

Чотири частини, порядок від найстабільнішого до найменш стабільного:
```
1. системна інструкція  ← кешується
2. правила поведінки     ← кешується
3. контекст (чанки)      ← змінюється
4. питання               ← змінюється
```
Той самий принцип, що в тижні 4 про кешування префікса: нестабільне внизу,
інакше кеш не працює і кожен запит платить повним prefill.

**Три правила в промпті:**
- відповідати тільки з контексту (інакше модель підмішує свої знання)
- казати «не знаю», коли контексту бракує
- цитувати джерело як `[1]`, `[2]` — єдиний спосіб перевірити відповідь

### Результати

**Цитування працює надійно.** Модель ставить `[1]`, `[2]` без додаткових
якорів — на відміну від «give an example» у тижні 4. Імовірно тому, що
нумерація фізично присутня в контексті: є за що зачепитись.

**Відмова працює чесно.** На питаннях поза корпусом модель відповідає
«The provided context does not contain this information», а не вигадує.

**3 чанки достатньо.** Більше — дорожче, не краще. Збігається з
`recall@3 = 0.94` із тижня 5.

**Query rewriting виявився непотрібним.** `"why divide by square root of d_k"`
і `"why scale the dot products"` дали однаково добрі відповіді. У тижні 5
перший провалювався — але там був чистий dense. Hybrid + reranker лагодять
саме цей випадок.
→ **краще полагодити retrieval, ніж обходити його переписуванням запитів**

### Єдина помилка: крос-документне забруднення

Питання: `"how many attention heads does the base Transformer use"`
Відповідь: `BERTBASE (L=12, H=768, A=12) uses 12 attention heads`
Контекст: `attention#15, bert#12, attention#14`

**Це не галюцинація.** Модель чесно відповіла з контексту й процитувала.
Правильний чанк `attention#14` (де `h = 8`) був третім, `bert#12` другим —
модель узяла перше правдоподібне число. У корпусі три статті, терміни
перетинаються: BERT теж має attention heads і конфігурацію.

**Промпт це не лагодить.** Додав правило «before answering, check that the
cited source actually discusses the subject of the question» — не допомогло.
→ та сама закономірність, що в тижні 4: **обмеження формату виконуються
  надійно, вимоги додаткової роботи губляться**. Семантичне зіставлення
  «BERT ≠ Transformer» за межею 3B

### Побічний результат: top_k=1 небезпечний

```
top_k=3:  attention#15, bert#12, attention#14  → неправильна відповідь
top_k=1:  attention#15                          → чесна відмова
```
З одним чанком правильний `attention#14` не потрапив у контекст взагалі.
Модель могла б щось вигадати з того, що було — але відмовилась.
→ `top_k=1` втрачає страховку на випадок помилки ранжування.
  Три чанки — розумний мінімум (MRR 0.72: правильне знаходиться,
  але не завжди першим)

### Варіанти фікса забруднення (відкладено)

| підхід | проблема |
|---|---|
| фільтр за `source` у Qdrant | треба знати документ наперед |
| класифікатор запиту → документ | ще один компонент, що помиляється |
| топ-N з кожного джерела окремо | контекст роздувається |
| більший reranker (bge-reranker-v2-m3) | 2.2 ГБ, не влазить |

**Рішення: відкласти.** Одна помилка на 16 питань, причина зрозуміла.
Ціна фікса непропорційна.

### Теорія: чи модель «знає, що не знає»

**Ні.** Механізму самоперевірки немає: вона генерує найімовірніший токен,
і для будь-якого питання правдоподібне продовження існує завжди. Відмова
в моєму пайплайні — не рефлексія, а виконання інструкції: порівняння
питання з текстом у промпті.

Непрямі сигнали на практиці: ентропія розподілу логітів (працює посередньо —
модель буває впевнено неправильна), самоузгодженість (кілька генерацій
із temperature > 0, дорого але надійніше), калібрування через тренувальні дані.

**Як вирішується, коли лізти в базу** — три архітектури:
1. **завжди шукати** (мій випадок) — просто, передбачувано, але платиш
   за retrieval навіть на «привіт»
2. **tool calling** — модель генерує спецтокен виклику пошуку. Рішення приймає
   той самий механізм передбачення наступного токена: вона навчена, що після
   питання про документацію статистично йде виклик пошуку
3. **маршрутизація перед моделлю** — дешевий класифікатор вирішує,
   чи потрібен retrieval

**Масштабування** — принципово так само. ChatGPT із пошуком робить те саме:
запит → пошук → контекст → генерація. Різниця кількісна. Що справді
масштабується інакше: розмір контексту (100k+ токенів), багатокрокове
міркування (агентний RAG), переписування запиту перед пошуком.


## 2026-10-05 — Тиждень 6, день 2: галюцинації і межі відмови

**Перевірено три типи небезпечних входів:**

| тип | приклад | результат |
|---|---|---|
| повна відсутність | питання поза корпусом | ✓ чесна відмова |
| правдоподібне, але відсутнє | learning rate для big моделі | ✓ чесна відмова |
| хибна передумова | «чому автори відмовились від attention на користь convolutions» | ✓ модель вказала, що такого в документі немає |

**Хибна передумова — найскладніший тест, 3B витримала.** Модель не вигадала
обґрунтування неіснуючого рішення, а назвала передумову неправильною.
Це вимагає зіставити твердження з контекстом і виявити суперечність.

**Цитування точне:** правильний чанк, зазвичай перший у контексті.

### Єдиний проблемний випадок

Питання про конфігурацію BERT — у контексті були і BERT-base, і BERT-large,
модель взяла large.

→ та сама закономірність, що вчора (BERT замість Transformer): **коли
  в контексті кілька однотипних конфігурацій, модель їх не розрізняє**.
  Вчора різні моделі, сьогодні різні розміри однієї
→ лікується не промптом, а точнішим retrieval або явною вказівкою
  в формулюванні питання

### Висновок

Генерація — не вузьке місце пайплайна. Усі помилки, знайдені за два дні,
походять із retrieval: у контекст потрапляє схожий, але не той факт.

→ пріоритет покращень: retrieval, не промпт
